# スケジュール実行（Playwright 版 / 仕様書 §7.1「補助方式B」）

決まった時刻に自動で会話を書き出す。Node から Chrome を**専用プロファイル**で起動し、
Teams を開いて収集し、指定フォルダに `.md` を保存する。

収集ロジックはブラウザ内実行とまったく同じもの（`dist/teams-collect-console.js` をページに流し込む）。
違いは「誰が起動するか」と「どこに保存するか」だけ。

> **2026-08-14 時点: 実機での動作確認は未実施。** 左一覧から会話を選ぶセレクタが未検証（後述）。

## 認証の扱い

**ID / パスワード / トークンは一切保存しない**（CLAUDE.md 原則2）。
行うのは「**人が一度ログインしたブラウザプロファイルを再利用する**」ことだけ。

- 初回は `npm run schedule:login` でブラウザが開くので、**自分でログインする**
- 以後 `npm run schedule` がそのプロファイルを使う
- 組織の設定（条件付きアクセス等）でセッションはいずれ切れる。切れたら**自動ログインは試みず**、
  理由を出して異常終了する。`npm run schedule:login` をやり直すこと

自動ログイン・MFA の自動化は行わない（「やらないこと」）。

## 準備

### 1. 設定ファイルを作る

`schedule.config.example.json` をコピーして `schedule.config.json` を作り、パスを自分の環境に合わせる。

```
copy schedule.config.example.json schedule.config.json
```

`schedule.config.json` と状態・ログのファイルは `.gitignore` 済み（保存先や会話 ID が入るため）。

| 項目 | 意味 |
|---|---|
| `profileDir` | 専用ブラウザプロファイルの置き場所。**普段使いの Chrome とは別にする**（同時に開けないため） |
| `outDir` | `.md` の保存先 |
| `stateFile` | 会話ごとの前回実行時刻。差分取得に使う |
| `logFile` | 実行ログ（JSON Lines で追記） |
| `overlapMinutes` | 差分取得の巻き戻し幅。既定 60 分 |
| `betweenTargetsMs` | 会話を切り替えるまでの待ち。低頻度・逐次のため |
| `targets` | 取得対象（下記） |

### 2. 取得対象を書く

```json
{
  "name": "DTS / 911_プロパー",
  "threadId": "19:5bd8f4d415f642f1949fbe396f62ff4d@thread.tacv2",
  "displayName": "911_プロパー(星野PL-R＆D)",
  "mode": "incremental"
}
```

- `threadId` は、**一度手で書き出した `.md` のフロントマター `thread_id`** からコピーできる
- `mode` は `incremental`（前回以降だけ）か `full`（毎回全件）
- `name` は状態の記録に使うので一意にすること
- `displayName`（任意）は左一覧に表示されている会話名。`threadId` で見つからなかったときの
  探索と、会話名が取れなかったときの補完に使う（「会話の選び方」参照）
- `threadId` の代わりに `"current": true` にすると、**そのとき開いている会話**をそのまま取る
  （会話の選択を行わないので、一覧の状態に左右されない）

### 3. ログインする

```
npm run schedule:login
```

ブラウザが開くので、Teams にログインして会話が表示されるまで待つ。
「サインインしたままにする」を選んでおくとセッションが長持ちする。

### 4. 手で 1 回実行してみる

```
npm run schedule
```

`outDir` に `.md` ができ、最後にサマリが出れば成功。**タスクに登録する前に必ず 1 回手で確かめること。**

## 設定ファイルを指定して実行する

引数を省くとリポジトリ直下の `schedule.config.json` を使う。別の場所・別の名前のファイルを使うときは
第 1 引数で渡す。

npm 経由の場合は **`--` を挟む**（前後は半角スペース）。`--` は「ここから先は npm ではなく
スクリプトへの引数」という区切りで、これが無いと npm 自身のオプションとして解釈され、
スクリプトには届かない。

```
npm run schedule -- C:/mytk/config/schedule.work.json
npm run schedule:login -- C:/mytk/config/schedule.work.json
```

| 書き方 | 結果 |
|---|---|
| `npm run schedule -- config.json` | 正しい |
| `npm run schedule --config.json` | npm のオプション扱いになり、スクリプトに渡らない |
| `npm run schedule config.json` | npm の版によっては渡らない。`--` を付けるのが確実 |

`--` の扱いを気にせずに済むので、直接呼ぶほうが確実。

```
node tools/scheduled-export.js C:/mytk/config/schedule.work.json
```

相対パスはカレントディレクトリ基準で解決される。

### 設定ファイルを複数に分ける

対象や頻度の違うジョブ（毎日の差分取得と、週次の全件取得など）は、設定ファイルを分けて
それぞれタスクに登録する。

そのとき **`stateFile` と `logFile` も必ず分けること。** 同じ状態ファイルを共有すると、
片方の実行が他方の差分取得の起点を動かしてしまい、取りこぼしが起きる。

## タスクスケジューラに登録する

Windows のタスクスケジューラで「基本タスクの作成」。

| 項目 | 値 |
|---|---|
| プログラム | `node`（または `C:\Program Files\nodejs\node.exe`） |
| 引数 | `tools\scheduled-export.js`（設定ファイルを指定するなら `tools\scheduled-export.js C:\mytk\config\schedule.work.json`） |
| 開始（作業フォルダ） | `C:\mytk\git\randd\teams-md-exporter` |

- **「ユーザーがログオンしているときのみ実行する」を選ぶ。** ブラウザに画面が要る
- 実行頻度は 1 日 1 回程度から。高頻度アクセスは行わない（CLAUDE.md「やらないこと」）
- 失敗すると**終了コード 1** で終わるので、タスクの「前回の実行結果」で気づける

## 結果の見方

| 表示 | 意味 |
|---|---|
| `✓` | 取得できた |
| `−` | 新着なし。差分取得では正常で、**ファイルは作らない**（空ファイルを量産しない） |
| `✗` | 失敗。終了コードが 1 になる |

`logFile` に 1 実行 1 行の JSON が追記される（対象・件数・範囲・警告の理由・所要時間）。

失敗と見なすのは **fatal が出たとき**（抽出 0 件、セレクタ未設定など）。
`truncated`（先頭まで遡れなかった）や未取得の返信は失敗にしないが、必ず理由として記録する。

**前回実行時刻は成功したときだけ進む。** 失敗時に進めると、次回の差分取得が失敗した区間を飛ばしてしまうため。

## 会話の選び方（`threadId` 指定）

> **2026-08-19: 実機で動作確認済み。**

左の一覧の項目は `data-fui-tree-item-value` に会話 ID を持っている。これを手がかりに対象を
クリックする。セレクタは `selectors.json` の `navigation` に外だししてある（コードに書かない）。

素直に一発で決まらない場面があったため、段階的に手を尽くす作りになっている。

1. `navigation.conversationListItem` のセレクタで探す（完全一致 → `|` 区切りの末尾一致 → 部分一致）。
   仮想リストの描画待ちがあるので、間隔を空けて最大 5 回まで試す
2. **クリックしたら、実際に会話が切り替わったかを確認する。** 送信ボタンの `data-track-thread-id` が
   対象の ID になるまで待ち、ならなければ次の候補へ進む（押せたことを成功と見なさない）
3. 見つからなければ、`threadId` の形からアプリビューを判定して切り替え、もう一度探す
   （`@thread.tacv2` / `@thread.skype` → チーム、`@thread.v2` / `@unq.gbl.spaces` → チャット）
4. `displayName` が指定されていれば表示名で探す。さらに `navigation.conversationSearchInput` が
   設定されていれば検索欄からも探す
5. それでも駄目なら失敗。エラーには左一覧の診断情報（項目の総数・一意数・完全一致の有無・
   部分一致したサンプル）を付ける。次に直すときの手がかりを残すため

**選択に失敗しても、そのとき開いている会話が対象と一致していればそのまま続行する**
（一致は `threadId` で判定する）。その場合は「左一覧の選択は失敗したが、開いている会話を使った」
という理由を実行ログに残す。黙って別の会話を取ることはない。

### 会話名が取れなかったときの補完

タブのタイトルから会話名を取れない場合（Teams の更新が遅れるなど）、対象設定の `name` /
`displayName` / 左一覧の行テキストの順に会話名として使う。使ったときは
`conversation-title-fallback`（info）を残すので、推測で埋めたことが後から分かる。

### うまく動かないとき

1. 対象を `"current": true` にする（選択操作を行わないので確実）
2. `displayName` を足す（表示名での探索と検索欄からの探索が有効になる）
3. エラーに出る診断情報を見て、`navigation.conversationListItem` を直す

## 保存したファイルの扱い

**会話の実データが定期的にディスクへ溜まる。** ブラウザ内実行と違い、無人で増え続ける点に注意。
保存先・保持期間・削除の要否は、仕様書 §10 と勤務先の情報管理規程に照らして決めること。
このツール側では古いファイルの自動削除は行わない（消す判断を勝手にしない）。
